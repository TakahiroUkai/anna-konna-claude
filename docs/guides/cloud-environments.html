Claude Codeのクラウド環境を読み解く:通信・変数・秘密の鍵・セットアップの仕組み

Claude Codeのクラウドセッションが動く「環境」の設定を、仕組みの面から整理しました。通信がどの道を通るか、設定がいつ反映されるか、秘密の鍵がなぜ見えないのか、セットアップスクリプトとキャッシュの関係を、図と表で読み解きます。

先に結論

クラウド環境は、クラウド上のパソコン(仮想マシン)がどう始まるかを決める設定のまとまりです。設定できるのは、次の4つです。

  • ネットワークアクセス: 外へ出る通信を、どこまで許すか
  • 環境変数: セッションに渡す設定値
  • ネットワークシークレット: Claudeには見せずに、API呼び出しにだけ付ける鍵
  • セットアップスクリプト: Claudeが動き出す前に走る準備の手順

ふだんは初期設定の「Default」のままで足ります。この解説は、設定の手順ではなく、設定がどう効くかを読み解きます。手順や、失敗しやすい例は、手順書「Claude Codeのクラウド環境を、初心者が失敗せずに設定する」(このページの下の「次に読む」から開けます)にあります。

公式ドキュメントの「Configure cloud environments」をもとに、2026年11月5日に確認した内容です。数値や画面の名前は変わることがあります。設定する前に、公式の最新版も見てください。

環境が使われる場所

クラウドセッションは、Claudeのデスクトップアプリ、スマホアプリ、ブラウザ(claude.ai/code)、ターミナルのclaude --cloud、クラウドの定期タスク、Slackの連携「Claude Tag」のどこから始めても、同じ「環境」の仕組みを使います。対象は、Pro、Max、Teamプランと、Enterpriseの一部の席です。

注意が2つあります。

  • Remote Controlは、手元のパソコンで動く会話を、スマホなどから操作する仕組みです。自分のパソコンの通信とファイルを使うので、クラウド環境は使いません。
  • 自分のサーバーで動かすセルフホスト環境にも切り替えられます。この解説は、Anthropicが用意する環境(Anthropic-hosted)を中心にしています。

セッションが始まるまでの順番

設定の効き方を理解する近道は、始まる順番を知ることです。

この順番から、次のことが分かります。

  • セットアップスクリプトは、環境変数が読み込まれる前に走ります。スクリプトで使う値は、スクリプトの中に書きます。
  • フックはClaude Codeが起動した後に走ります。起動のたびに動くので、重い処理は向きません。
  • ネットワークシークレットは、Claude Codeが起動した後に使われます。セットアップスクリプトの通信には付きません。

通信がたどる道:ネットワークアクセス

環境ごとに、外へ出る通信の許可レベルを1つ選びます。

ここで大事なのは、通信の道は1本ではないことです。4つの道は、許可レベルとは別に動きます。

この仕組みから、よくある疑問に答えられます。

  • Noneにしたのに、GitHubは使える: GitHubの通信は、専用のプロキシ経由の別の道だからです。
  • コネクタの宛先を、許可リストに足さなくてよい: コネクタの通信は、Anthropicのサーバーを通るからです。使わないコネクタは、オフにしておきます。
  • 変更は新しいセッションを待たなくてよい: ネットワークアクセスを変えると、動いているセッションにも、1分ほどで反映されます(許可リストを通る通信について)。

許可リスト(Custom)の書き方も押さえます。1行に1つのドメインを書き、先頭の*.で、すべてのサブドメインを表します。初期の一覧も使いたいときは、「Also include default list of common package managers」にチェックを入れます。組織全体に1つの一覧を配る仕組みはないので、チームで揃えたいときは、Ownerが共有環境を作ります。

設定値の渡し方:環境変数

環境変数は、KEY=valueの形で1行に1つ書きます。#は、引用符で囲まない値の中では、コメントの始まりとして扱われます。#を含む値や、複数行の値は、引用符で囲みます。

覚えておきたいのは、次の3点です。

  • 誰でも読める: その環境を使う人は、値を読めます。秘密の鍵は、ここに入れません。
  • すぐには反映されない: 編集しても、動いているセッションは、読み込み済みの値を使い続けます。値が読み直されるのは、休止していた仮想マシンが戻るとき、または作り直されるときです。すぐ試したいときは、コマンドの前に値を付けるか、新しいセッションを始めます。
  • 一部は渡されない: OTEL_*で始まる変数は、Claude Code自身の記録の送信に使われ、Claudeが実行するコマンドには渡されません。

見せずに使う鍵:ネットワークシークレット

APIの鍵を環境変数に入れると、Claudeにも、その環境を使う人にも見えてしまいます。ネットワークシークレットは、これを避けるための仕組みです。

使い方の要点は、次のとおりです。

  • 入力する項目は、名前、使うホスト(api.example.comのように。*.で全サブドメインを表せる)、鍵を入れるヘッダーです。初期の型の「Bearer」は、AuthorizationヘッダーにBearerを付けて鍵を送ります。X-Api-Keyのように前置きが要らない鍵は、名前を変えて、前置きを消します。
  • 追加は1件ずつです。ホストや値を変えたいときは、消して入れ直します。
  • 動作確認は、新しいセッションでClaudeにcurlで呼んでもらいます。APIは鍵つきとして答え、鍵そのものは環境変数にもファイルにも現れません。

付かない相手もあります。GitHub(専用プロキシが別に処理します)、Anthropic API、主要なパッケージ置き場(npm、PyPI、crates.ioなど)、セットアップスクリプトの通信、Claude Code自身の記録の送信です。これらには、鍵が付きません。GitHubの鍵が必要なときは、シークレットではなく、次のGitHubの仕組みを使います。

利用できる人にも条件があります。ProとMaxのプラン、Teamのプランでは、自分の環境に追加できます。Enterpriseでは、組織の管理者の役割が要ります。セルフホスト環境には、この仕組みはありません。また、組織が自分で管理する暗号鍵を使っている場合は、保存できません。

GitHubの通信:専用プロキシ

Anthropicが用意する環境では、GitHubへの通信はすべて専用のプロキシを通ります。本物のGitHubの認証情報は、仮想マシンの外に置かれます。

  • 仮想マシンの中のgitは、範囲を絞った一時の認証情報を使います。プロキシが、それを本物のトークンに差し替えます。
  • 押し込める先に制限があります。ブランチの削除と、タグなどブランチ以外の押し込みは、断られます。どのブランチに押し込めるかは制限されないので、守りたいブランチは、GitHub側の保護ルールで守ります。
  • 対象は、セッションに結びつけたリポジトリだけです。ほかのリポジトリのAPIは、403で断られます。公開リポジトリでも同じです。
  • GitHubのGraphQLは使えません。gh prやgh issueのようにGraphQLを使うコマンドは、403になります。代わりに、gh api repos/{owner}/{repo}/...のREST形式を使います。

GH_TOKENやGITHUB_TOKENを自分で設定しなければ、これらの変数はproxy-injectedという置き物の文字列になります。実際の認証は、プロキシが外で行います。自分で設定した場合は、ふつうの環境変数なので、その環境を使う人に見えます。

最初から入っているもの、手元から届くもの

仮想マシンは、セッションごとに新しく作られます。Ubuntu 24.04、x86_64で、手元のパソコンの種類には関係しません。

入っていないもの(.NET SDKなど)は、セットアップスクリプトで入れます。データベースは、Claudeに頼んで起動してもらいます。

では、自分の手元の設定は、クラウドに届くのでしょうか。基本は「リポジトリに入れたものだけ届く」です。

手元の設定を、リポジトリに入れずに使いたいときの抜け道が、セットアップスクリプトです。スクリプトの中で~/.claude/CLAUDE.mdを書けば、個人用の指示としてセッションに読み込まれます。ただし、スクリプトも誰でも読めるので、共有環境ではなく、自分の環境に置きます。

準備の手順:セットアップスクリプトとキャッシュ

セットアップスクリプトは、セッションの始まりに1度走る、Bashの手順です。root権限で走るので、apt installも使えます。

守る条件は、4つです。

  1. 最後に成功で終わる: 終了コードが0以外だと、セッションが始まりません。なくても困らない処理には、末尾に|| trueを付けます。
  2. 5分ほどで終わる: 長すぎると、キャッシュが作られません。独立した導入は&とwaitで並べて走らせます。
  3. 通信が必要: Noneでは、導入が失敗します。Trustedなら、npm、PyPI、RubyGems、crates.ioなどに届きます。
  4. 環境変数は、まだ無い: 必要な値は、スクリプトの中に書きます。

キャッシュは、セットアップが5分ほどで終わったときに、ファイルの状態を丸ごと保存して、次からそこを出発点にする仕組みです。自分で有効にしたり、管理したりする必要はありません。

キャッシュは、次のときに作り直されます。

  • セットアップスクリプトを変えたとき
  • 許可するホスト(ネットワーク設定)を変えたとき
  • 作ってから、約7日がたったとき

すでに動いているセッションには、スクリプトの変更は届きません。 休止から戻るときにも、スクリプトは走りません。すぐ反映したいときは、セッションの中で同じコマンドを実行するか、新しいセッションを始めます。

セットアップスクリプトとSessionStartフックの使い分け

フックでクラウドだけに限りたいときは、スクリプトの先頭で、環境変数CLAUDE_CODE_REMOTEがtrueでなければ、すぐ終わるようにします。クラウドではtrueになり、手元ではtrueになりません。

フックには制約もあります。複数のリポジトリを結びつけたセッションと、プロジェクトのクラウドスレッドでは、リポジトリのフックは走りません。その場合は、セットアップスクリプトを使います。

上限と時間

コマンドの待ち時間を長くしたいときは、環境変数のBASH_DEFAULT_TIMEOUT_MSとBASH_MAX_TIMEOUT_MSを足します。単位はミリ秒です。それでも足りない作業は、自分のパソコンで動かすRemote Controlか、セルフホスト環境を考えます。

作り直し・やめるとき

環境は、削除ではなくアーカイブします。アーカイブすると、新しいセッションは始められなくなり、画面の一覧と/remote-envからも消えます。動いているセッションは続きます。ネットワークシークレットも、動いているセッションには付いたままなので、不要な鍵は先に消します。

定期タスクなど、環境を指定している仕組みは、アーカイブした環境では新しいセッションを始められません。別の環境に付け替えます。

注意すること

  • 環境変数とセットアップスクリプトは、その環境を使う人全員が読めます。共有環境には、秘密の鍵を入れません。
  • 「Full」は、どのドメインにも出られます。必要な理由があるときだけ使い、できるなら「Custom」で絞ります。
  • 画面や名前、上限の数字は、変わることがあります。設定する前に、公式ドキュメントで最新の内容を見てください。
